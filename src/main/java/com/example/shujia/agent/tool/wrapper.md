# ToolWrapper 的三种改进方向

## 1. 现状：`@Tool` 集中在 ToolWrapper
- **优点**：审计 / 计时 / 异常记录集中在一处，好维护。
- **缺点**：加新工具要改 **2 处**（新建 impl 类 + 在 ToolWrapper 里加一个 `@Tool` 方法）。

## 2. `@Tool` 下放到每个工具类
- **优点**：加工具只改 **1 处**。
- **缺点**：
  - 丢掉 ToolWrapper 里**集中的审计 / 计时 / 异常记录**逻辑（除非在每个工具里手写一遍 → 重复代码）。
  - `ChatConfig` 要从 `.defaultTools(toolWrapper)` 改成**收集所有工具实例**再一起传给 `defaultTools(...)`，否则模型看不见。

## 3. `@Tool` 下放 + AOP 切面（`@Aspect`）统一接管审计
- **优点**：加工具只改 **1 处**；审计 / 计时仍然集中（收进切面里）；工具类只管业务，不掺横切逻辑。
- **代价**：多学一个 AOP，切面写错会影响所有工具。
- **结论**：**最干净的方案**。

---

## 补充：为什么"计时写在每个工具里"不好
不是"繁琐"，是**重复会扩散**：
- 想改日志格式 / 加 traceId → 要挨个改 N 个文件，漏一个就不一致。
- 新加工具容易**忘抄**审计段 → 该工具没审计，还不易发现。
- 业务逻辑和审计混在一起，可读性差。

**取舍**：3 个工具且不再扩展 → 手写也行；工具会持续加 / 想体现工程思维 → 上 AOP（写一次，常数代价）。
